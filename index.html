Target state + implementation roadmap

Evergreen Rebase / Repave

A target-state platform for continuously identifying base-image drift across application environments, controlling when remediation may begin, and safely orchestrating rebase and repave workflows at firm scale — while evolving the live platform incrementally without disrupting existing customers.

Core design principle Separate identifying work from executing work.
Operating model State → Eligibility → Admission → Execution

Target architecture

The platform can immediately understand the full remediation backlog without creating a firm-wide execution spike.

Architecture diagram

A high-level system view showing how onboarding and environment events establish state, how user and firm policy determine eligibility, and how scheduling protects execution capacity.

State management determines whether action is required. Eligibility and governance apply wave timing, manual authorization and user deferral policy. Scheduling controls how much eligible work may enter Temporal. Durable states make normal waiting, intentional deferral, policy exception and technical blockage visibly distinct.

Application team user journey

Users onboard through configuration; after that, the platform continuously maintains base-image currency for each environment.

01 · Onboard

Commit evergreen.yml

Application team declares the component and environments.

02 · Discover

Establish environment truth

Platform discovers deployed application images, observed base images and execution policy.

03 · Evaluate

Determine need

Observed state is compared with the current desired base image.

04 · Queue

Enter pending execution

If remediation is needed, the environment becomes a durable backlog item.

05 · Control

Determine eligibility

Automated environments wait for their wave and may be deferred within policy; manual environments wait for user input.

06 · Admit

Apply load controls

The scheduler admits work only when runtime capacity allows.

07 · Execute

Run Temporal workflow

Rebase, repave and validation are orchestrated to completion.

08 · Complete

Reach a durable outcome

The environment returns to up-to-date, or is surfaced as exception or blocked when governance or intervention is required.

Waves and scheduling

Wave timing controls rollout eligibility. The scheduling service independently controls actual execution volume.

Automated environment Wave-driven

PENDING_EXECUTION → wait for wave open time → optionally defer within policy → scheduler capacity → execute.

Manual environment User-driven

PENDING_EXECUTION → wait for user trigger → scheduler capacity → execute immediately when room exists.

Example rollout waves

Wave 1Monday · 09:00
Wave 2Monday · 13:00
Wave 3Tuesday · 09:00

A wave opening means work may start. It does not directly start all environments in that wave.

Manual work may use any free capacity. The reserve only prevents automated workloads from consuming the final protected slots.

Runtime controls can be increased or decreased without restarting services. Lowering limits does not cancel active workflows; it only reduces new admissions.

Application control & exception governance

Automated remediation remains the default, while application teams retain bounded control to defer a repave when timing conflicts with their workload or business activity.

Normal

PENDING_EXECUTION

Work is required and is waiting for its normal execution conditions: wave eligibility and scheduler capacity.

User controlled

DEFERRED

The application team has intentionally postponed an automated repave within the firm's permitted deferral policy.

Governance

EXCEPTION

The environment has exceeded the permitted deferral allowance or firm remediation standard and requires governance visibility.

Deferral principles

  • Deferral applies to automated repaves before scheduler admission.
  • Deferrals are time-bound and governed by a firm-defined allowance.
  • When the permitted defer period expires, the environment returns to PENDING_EXECUTION.
  • A newer desired base does not erase the unresolved remediation obligation.

Exception vs. blocked

EXCEPTION is a governance condition: remediation is overdue relative to firm policy.

BLOCKED is an operational condition: automation cannot safely continue because technical or manual intervention is required.

Continuous reevaluation: DEFERRED and EXCEPTION remain evaluatable. If a normal application deployment brings the environment onto the desired base image, the state can return directly to UP_TO_DATE.

Current → Target migration

The implementation is not a rewrite. Each slice is inserted into the current customer-serving flow, initially preserving today’s behavior before taking on additional responsibility.

Slice 1

Onboarding & Discovery

Introduce a new source of environment truth without initially changing the downstream scheduling behavior customers rely on today.

Crawl

Introduce evergreen.yml onboarding

  • Consume evergreen.yml from the application Git repository
  • Validate onboarding configuration
  • Discover configured environments
  • Collect the information required by current onboarding
  • Call the existing Evergreen schedule workflow the same way onboarding does today
Outcome A new onboarding mechanism is introduced with no downstream execution behavior change.
Walk

Make discovery event-driven

  • Ingest external deployment events
  • Ingest new base-image events
  • Use those events to refresh environment truth through the discovery flow
  • Continue invoking the existing Evergreen schedule workflow
  • Prove event-driven discovery before changing decision ownership
Outcome Discovery becomes continuously updated while execution remains backward compatible.
Run

Feed the State Machine

  • Discovery stops deciding that work should execute
  • Emit/update canonical environment facts
  • Provide application image, observed base and desired base
  • Provide automation type and environment configuration
  • State Machine becomes the consumer of discovery results
Outcome Discovery owns truth; lifecycle decisioning moves cleanly into Slice 2.

Slice 2

State Machine

Introduce explicit lifecycle decisioning while preserving the current “repave when needed” execution behavior first.

Crawl

Introduce core lifecycle states

  • Add DISCOVERY
  • Add UP_TO_DATE
  • Add REPAVE_NEEDED
  • Add BLOCKED
  • Evaluate observed vs desired state
  • When REPAVE_NEEDED, immediately call the Evergreen schedule workflow
Outcome Decision ownership moves into the State Machine without changing current scheduling behavior.
Walk

Add user deferral & governance

  • Add DEFERRED
  • Add EXCEPTION
  • Allow users to defer automated remediation
  • Enforce firm-defined deferral limits
  • Move overdue remediation into EXCEPTION
  • Keep technical failures distinct in BLOCKED
Outcome The lifecycle now represents user intent and firm remediation policy.
Run

Close the loop with Temporal

  • Consume Temporal workflow callbacks
  • Add non-prod execution states
  • Add production execution states
  • Introduce evaluatable states
  • Reevaluate new base / deployment information in safe states
  • Make lifecycle state authoritative end-to-end
Outcome State reflects both external environment truth and active workflow progress.

Slice 3

Scheduling Service

Introduce the scheduling layer first as a pass-through seam, then progressively make it responsible for execution eligibility and firm-scale rollout controls.

Crawl

Pass through fully automated work

  • Receive the relevant execution-ready state
  • Support fully automated environment types first
  • Forward eligible work immediately to Temporal
  • Preserve current customer execution timing
  • Create the architectural seam for future policy
Outcome The scheduling service sits safely in-path without materially changing customer behavior.
Walk

Respect user deferrals

  • Take State Machine deferral outcomes into account
  • Do not schedule DEFERRED work
  • Do not schedule BLOCKED work
  • Keep deferral policy calculation in the State Machine
  • Forward eligible fully automated work to Temporal
Outcome User control is honored without duplicating governance logic in the scheduler.
Run

Add waves, capacity & manual override

  • Introduce timed waves by environment
  • Apply configurable concurrency limits
  • Allow limits to change dynamically with platform load
  • Add start-rate and automated pause controls
  • Allow manual execution to bypass wave timing
  • Reserve capacity for manual user-triggered work
Outcome Scheduling becomes the firm-scale rollout and load-protection control plane.

Crawl / Walk / Run summary

The roadmap shows both the target capability and how each slice fits safely into the current platform while it is being introduced.

Implementation principle: each new architectural layer is first inserted in compatibility mode. Once it is proven, the next increment moves more decision-making into that layer without requiring a disruptive rewrite of the existing Evergreen platform.

Combined takeaway

Evergreen continuously identifies which environments require remediation, but deliberately separates that determination from execution. Timed waves govern automated rollout, users can temporarily defer automated work within firm policy, exceptions make overdue remediation visible, manual users retain a responsive execution path, and dynamically configurable scheduler limits protect shared infrastructure from firm-wide load spikes.
